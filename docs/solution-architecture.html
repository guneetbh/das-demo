Personalisation Assistant — End-to-End Solution Architecture

One agentic capability, built once on a governed agent platform and a single data spine, that personalises discovery, sizes every customer, sells services with consent and rewards loyalty, and that can be sold beyond our own estate. This page describes the solution as built in branch feature/target-architecture.

1Business context

Neu.Tail is a UK fashion retailer that has chosen to be a digital platform with stores, with 38 stores acting as fulfilment, experience and trust nodes. The Personalisation Assistant is the capability that makes that platform intelligent by default.

Problem statement

Customers aren't understood
  • The feed is generic, so engagement falls.
  • Identity and basket reset between app, web and store.
  • Nothing a customer did yesterday shapes today.
Returns erode margin
  • 34% of orders come back, mostly wrong size.
  • Return reasons are captured but not learned from.
  • No per-customer fit guidance exists before purchase.
Value is left on the table
  • No paid service layer (styling, guarantees, access).
  • Loyalty accrues points but doesn't engage.
  • Risky charges are checked manually or declined falsely.

Profiling & segmentation

UC2
Personalised discovery

Size & fit
TAILOR · supported by GRADE (return reasons)
UC4
Service upsell & monetisation
CONCIERGE · hosted by CARE, approved by SENTRY
UC5
Loyalty & gamification
TALLY · consumes the PERSONA segment

Commercial model: one capability, three widening rings

Ring 1 · B2C
Free personalisation, paid services

Neu.Tail+ and Elite subscriptions sold by CONCIERGE only on explicit consent; free tier funded by conversion and fewer returns.

Ring 2 · B2B open API
Agents as APIs

"Size & Fit as a Service" (TAILOR) and "Segmentation as a Service" (PERSONA), exposed today through the authenticated MCP adapter.

Ring 3 · B2B2C
White-label platform

The whole estate on a retailer's catalogue. The moat is outcome-based pricing on returns via the GRADE→TAILOR loop.

Scope, stakeholders and constraints

In scope (built)
  • Lead Orchestrator and 7 Personalisation agents.
  • 4 supporting agents as thin stubs with real contracts.
  • Agent platform: runtime, policy, audit, gateway, prompts, memory, vector retrieval.
  • Storefront, review console, admin console and an external MCP adapter.
Stakeholders
  • Shoppers (loyalty members, new customers).
  • Store and service colleagues acting as human reviewers.
  • Merchandising, finance and risk (outcomes, approvals).
  • Ring 2/3 partners (API consumers).
Constraints
  • Demo scale: runs on one laptop with zero required services.
  • Every live dependency (LLM, Redis, Chroma) is optional and has a deterministic fallback.
  • All data is synthetic, and no real PII is used.
  • The remaining 6 agents of the 17-agent estate are out of scope.

Architecture principles applied

One chokepoint
Every tool call goes through runtime.invoke(), which does the policy check, binds the customer, validates input, scopes data access and writes the audit entry.
Identity is never self-declared
The principal comes from the token or API key, or from the runtime when one agent calls another. It never comes from a request body.
Money moves on consent
Offers are read-only. Commits need an explicit action, pass SENTRY, run in one transaction and are idempotent.
Degrade, don't fail
LLM, Redis and Chroma are all optional. Each has a deterministic fallback, and every use of a fallback is logged.

Security: identityNo caller can act as another principal or another customer. Shopper token (HMAC-signed, customer-bound) or staff API key resolves to the principal; the runtime switches to the owning agent for nested calls; shopper contexts can't name a different customer. tested forged caller, cross-customer read and storefront→earn_points all denied (403). OIDC/IdP login, mTLS between services, secrets in a vault.
Security: authorisationLeast privilege on tools and data. Default-deny tool ACL per contract plus the slide-7 data-domain matrix enforced in the data-access layer; contracts claiming ungranted domains fail at import. tested DataAccessDenied outside scope / undeclared domain. Externalise to OPA/Rego with the same matrix as data.
Privacy & consentPII minimised; marketing needs consent. CARE masks contact data; upsell gated on marketing_consent; audit details redacted (hashed customer IDs, contact fields dropped, lists truncated). tested no raw ID or email in trace rows; Elena (no consent) gets no offer. DPIA, retention schedules, right-to-erasure job, field-level encryption.
Financial integrityNo double charge, no lost points, no unauthorised spend. Server-side pricing; pydantic bounds; one DB transaction per commit; idempotency keys; compare-and-set on offers/escalations; ledger UNIQUE(source, ref_id). tested 4 concurrent approvals → 1 order; 10 concurrent earns → exact sum; replay → same order. Payment-gateway idempotency, outbox to ERP/ledger.
Human oversightRisky charges are reviewed by a person. SENTRY risk score (amount bound, first-time payer, multiple of average order, velocity, tenure) escalates ≥ 0.5 to the review queue; reviewer identity comes from the staff key. demoed Amara's £90 Elite plan → queue → approve → order + points. Case management integration, SLA alerts, four-eyes for high value.
PerformancePages feel instant; a live model is only used where it adds value. Recommendation rows use the deterministic ranker (no model on page load); single-query stock filter; fit profile cached per category in MUSE's loop; candidates capped at 60 before any prompt. indicative ~220 ms for a full discovery turn on fallback; seed ~1 s. Streaming responses, response cache, feature store, async event bus.
Availability & resilienceThe journey still works when a dependency is down. Gateway tries providers in order and then a fallback; Redis re-probed after 30 s; Chroma falls back to token overlap; server-side refusal fallback on Opus 5.5. demoed whole suite and demo run with no keys, Redis or Chroma. Multi-AZ, circuit breakers, health-based routing, chaos tests.
ScalabilityGrow from demo to 820K members. Stateless API; customer-scoped session keys; data behind a domain DAL, so stores can be swapped per domain. demo scale SQLite (WAL), single node. Postgres per domain, Redis cluster, managed vector DB, horizontal API pods.
ObservabilityAny answer can be explained end to end. Single audit writer with trace_id, kind, latency, model and prompt version, outcome; writes deferred until after the transaction so a rollback never erases them. tested one trace links segment → retrieval → SCOUT/PACE → TAILOR → model → rank. OpenTelemetry export, dashboards, eval harness on prompt changes.
AI governancePrompts and models are governed, swappable and safe. Capability→model map in config; versioned prompt registry with a shared guard prompt; input cleaning; output filters (URLs, unsupported prices, length). built every model row carries prompt_version. Prompt A/B with offline evals, red-team suite, drift monitoring.
MaintainabilityAgents can change without touching each other. Each agent = contracts + handlers; stubs give real seams for SCOUT/PACE/GRADE/ONEBASKET; orchestrator holds no agent logic. built 11 agents, 20 tool contracts, one registry. Contract versioning, consumer-driven contract tests.
Testability & repeatabilityDeterministic, reproducible demos and tests. Fixed-seed causal data generator; throwaway test DB; live models disabled under test. 28 tests pass in ~3 s. CI pipeline, load tests, synthetic monitoring.
InteroperabilityPartners can consume agents as APIs (Ring 2). Authenticated MCP adapter exposing read-only contracts; same policy as internal calls. demoed no key → 401; reads OK; writes denied. API gateway, metering per call, partner tenancy.
CostPay for intelligence only where it earns its keep. Fast tier for routing and note blending; reasoning tier only for typed search ranking and offer pitches; Opus 5.5 at medium effort. by design zero model calls for home-page rows. Per-route effort tuning, prompt caching, cost dashboards.

5Conclusion summary

What the architecture delivers

  • All five functionalities run end to end: personalised discovery, per-customer fit, consent-based upsell with human review, a learning returns loop and gamified loyalty.
  • Governance is enforced, not just drawn: one runtime chokepoint, identity the caller can't forge, a tool ACL plus the slide-7 data matrix, a redacted audit trail with end-to-end traces.
  • Commerce you can trust: server-side pricing, single-transaction commits, idempotency and compare-and-set, all proven under concurrency in tests.
  • The business case is measurable: on the causally simulated estate, guided orders return ~14% against a ~35% baseline, the signal behind Ring 2/3 outcome-based pricing.
  • Resilient and cheap to run: every live dependency is optional, and model use is targeted to where it adds value.

What comes next (production path)

  • Identity & policy: replace demo login with OIDC, externalise policy to OPA, and keep the same matrix as data.
  • Data spine: move to Postgres per domain, a real-time CDP/feature store and a managed vector DB, with an event bus for GRADE/SCOUT signals.
  • Deepen the stubs: GRADE vision grading (vision tier already mapped), live SCOUT trend, PACE price pacing in the ±5% band.
  • AI assurance: an offline eval set per prompt, prompt A/B tests, red-teaming, and OpenTelemetry export of the existing traces.
  • Ring 2 go-to-market: API gateway, per-call metering and partner tenancy on top of the MCP adapter.
Bottom line: the Personalisation Assistant is built once on a governed agent platform. It understands each customer, sizes them before they buy and only charges with consent. It is safe to extend from our own 820K members (Ring 1) to partners as APIs (Ring 2) and to a white-label platform (Ring 3), and the GRADE→TAILOR returns loop is the differentiator a software-only rival can't copy.
