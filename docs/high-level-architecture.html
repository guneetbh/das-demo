Overview

Neu.Tail is a multi-agent retail assistant: seven specialist agents behind one policy-checked runtime chokepoint, real semantic product search over a local vector database, multi-intent request handling with a result composer, human-in-the-loop governance for anything outside policy bounds, and — as of this build — MCP as the literal transport for both internal agent-to-agent dispatch and external integration, not just an external add-on.

It runs standalone on one seeded SQLite file, with no required external services: Redis, a live model provider, and the MCP layer are all optional, each with a deterministic local fallback, so the system degrades gracefully rather than breaking when something it doesn't own isn't reachable.

Access & Policy as Code

neutail/policy.py is an embedded, default-deny rule evaluator — a real caller/tool allow-list, not OPA/Rego. Every tool is registered once, in contracts.py, with an explicit list of caller identities allowed to invoke it:

contracts.register(
    "rank_products",
    allowed_callers=["muse_agent", "lead_orchestrator"],
    handler=_rank_products,
)

runtime.invoke_tool(caller, tool, **kwargs) is the one chokepoint every call — internal or via MCP — passes through: it checks policy.check_tool_access() first, raising PolicyDenied if caller isn't on that tool's list, then calls the handler, then unconditionally writes an audit_log row — success or denial, no exceptions. A newly added caller has zero access to anything until explicitly allow-listed; nothing is over-permissioned by default.

Honest limit, stated plainly rather than glossed over: caller is self-declared by whoever calls — over HTTP (POST /tools/{name}/invoke) or over MCP. There's no authentication layer verifying a caller actually is who it claims. Fine for this demo, where the runtime itself is the trust boundary; not fine if either transport were ever reachable by an untrusted client without an auth layer in front of it.

What policy does not cover, also worth being precise about: model calls (gateway.call_model()) are logged to the same audit trail, but are not gated by the allow-list mechanism — there's no "which agents may call the reasoning tier" policy today, only "which agents may call which tool."

Memory & Context

Two tiers, deliberately not one, and the distinction is load-bearing: short-term (session) — segment, last_results, last_category_by_sku, keyed by session_id, in session_store.py. Redis with a 30-minute TTL when reachable (checked once per process via ping(), cached for that process's lifetime), else the session_context table in SQLite — same live/fallback shape as everything else in this codebase. This is what makes "the second one, in my size" resolve without restating anything, and what the fit handler reads in the multi-intent path to resolve against the discovery handler's just-shown results.

Durable (long-term) — customers, loyalty, fit_profile, behavioural, transactional, returns in SQLite, read live on every call, never cached. Nothing about personalization — segment, fit guidance, loyalty tier — depends on session memory surviving; a brand-new session_id for the same customer recomputes identically, verified by clearing the session and re-running the same search. A Redis restart erasing every active session cannot erase a customer's actual history, because history was never stored there.
